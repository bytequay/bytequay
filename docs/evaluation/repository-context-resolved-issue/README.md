# Closed-issue learning and reuse case

This case checks that an explicitly selected **closed issue** can become source-backed repository knowledge and that a later development task can find and open that note. It uses a disposable three-file repository, a read-only local GitHub API fixture, a read-only local HTTPS Git remote, and an isolated ByteQuay database. Nothing is sent to GitHub. [result.json](result.json) records the observed Learn and reuse receipts; it is a single acceptance observation, not a general quality score.

The repository's `contains(start, end, sample)` includes both boundaries. Its ordinary tests omit `sample == end`. Issue `contextfixture/issue-case#12` asks whether adjacent dashboard panels should stop sharing that sample. Cached activity contains a maintainer comment (`1201`) deciding to keep the inclusive end and a close event (`1202`) saying there was no code fix. The issue is `CLOSED` and is **not** a pull request. The note must report that decision as history; closure alone cannot establish that the code is fixed or that the decision still applies.

## Reproduce in a disposable directory

Use the scripts in this directory and a newly built `backend/app/target/bytequay-backend.jar`. The backend helper uses the existing ByteQuay Claude profile; a live provider run requires that profile to be ready. Keep all runtime files, tokens, responses, and logs under `/private/tmp`, outside this directory.

1. Run `python3 -B fixture.py create "$CASE_ROOT/corpus"` with `CASE_ROOT=$(mktemp -d /private/tmp/bytequay-resolved-issue-XXXXXX)`. This fixes the baseline commit and writes a manifest. Initialize a bare repository at `$CASE_ROOT/remote.git`, push `HEAD:refs/heads/main` from `$CASE_ROOT/corpus/repository`, set the bare `HEAD` to `refs/heads/main`, and run `git --git-dir "$CASE_ROOT/remote.git" update-server-info`. Do not add a remote to the frozen corpus repository.
2. Make a one-day self-signed certificate for IP `127.0.0.1` (`git-cert.pem`, `git-key.pem`); start `python3 -B fake_git.py "$CASE_ROOT"`. It writes `git-port`. Clone `https://127.0.0.1:$(cat "$CASE_ROOT/git-port")/remote.git` into `$CASE_ROOT/workspaces/issue-case/repository` with `GIT_SSL_CAINFO="$CASE_ROOT/git-cert.pem"`. Check `git ls-remote` with the same CA file. The local HTTPS URL must be both the checkout's `origin` and the workspace's `origin_clone_url`; otherwise the normal workspace synchronization cannot start a task.
3. Make a separate self-signed certificate with DNS SAN `api.github.com` (`github-cert.pem`, `github-key.pem`) and import it into `$CASE_ROOT/truststore.p12` with password `changeit`. Start `python3 -B fake_github.py "$CASE_ROOT"`; it writes `proxy-port` and serves only fixture GET requests. Put a random session value in `$CASE_ROOT/session.token`, copy the built JAR to `$CASE_ROOT/backend.jar`, and start `python3 -B start_backend.py "$CASE_ROOT" create`. Write the `BYTEQUAY_BACKEND_PORT` printed by the server to `$CASE_ROOT/backend-port`, then stop the server. The helper isolates Java user home, SQLite, workspaces, agent runtime, and Git CA settings.
4. Run `python3 -B seed_fixture.py "$CASE_ROOT/fixture.db" "$CASE_ROOT/corpus" "$CASE_ROOT/workspaces/issue-case/repository" "https://127.0.0.1:$(cat "$CASE_ROOT/git-port")/remote.git"`. It seeds only the disposable Hibernate-created database and writes the managed-workspace marker. Start `start_backend.py "$CASE_ROOT" update`, again recording its printed backend port. Save `{"value":"fixture-token"}` under `$CASE_ROOT` and submit it to `POST /api/auth/github/token` with `api_client.py`. The fake proxy validates the token through `GET /user`; no real token is needed.
5. Read `GET /api/repos/contextfixture/issue-case/issues/12/preview` and `GET /api/workspaces/issue-case/issues/12/detail` through `api_client.py`. Confirm `state=closed`, no `pull_request`, and comment `1201`. Start `POST /api/workspaces/issue-case/repository-context/build` with `scopeIds:["project"]`, `history:[{"kind":"ISSUE","number":12}]`, a unique `requestKey`, and the displayed `expectedRevision` and `expectedBuildSequence`. Poll the build GET until the result is `READY`, then read `GET /api/workspaces/issue-case/repository-context`.
6. Start one fresh `/agent/tasks` development task asking whether changing `window.py` to an exclusive end preserves the intended dashboard behavior, and ask the agent to check saved context and its original evidence without editing or publishing. Set `developmentAutomation.autoDraftPr=false` and `autoCiFix=false`. After its turn completes, read `/agent/tasks/{taskId}/repository-context?workspaceId=issue-case` and `/api/workspaces/issue-case/repository-context/usage?window=30d`. Inspect the final answer through `/agent/tasks/{taskId}/events`.

`api_client.py` accepts `runtime METHOD /path output.json [--body request.json]`, adds the session header from the disposable runtime, and writes responses only there. `fixture.py verify "$CASE_ROOT/corpus"` checks the frozen files, commit and ordinary test behavior independently of ByteQuay. Its manifest can be compared with the baseline and blob IDs in the notebook.

## Observed result and limits

Learn produced `knowledge:project` version `1`, citing the exact issue reference (`repositoryId=207`, issue `12`) and three frozen repository files. Its `RECORDED_DECISION` claim says the maintainer closed the issue without a code fix and kept the inclusive end pending a new decision. An `INFERENCE` claim notes that the README does not actually state that rule. The later task received confirmed `OFFER`, `SEARCH`, and `READ` receipts for the same note version, then explained why the exclusive-end change would reverse the recorded outcome.

The activity cache cannot prove pagination completeness or that no newer decision exists. The agent's answer did not claim closure meant a fix. The read-only task made no code change, so the separate development-result automation had no valid implementation result to report; its provider turn itself completed. Initial setup attempts failed before the successful Learn/reuse sequence because the managed-workspace marker was missing and then the fake repository's clone URL did not match the local Git remote; request-log counts include those attempts. This fixture does not test real GitHub connectivity, issue freshness, or statistical answer quality.
