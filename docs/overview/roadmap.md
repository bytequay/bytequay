# Remaining work and verification limits

ByteQuay is pre-1.0. Existing code, design intent, and release verification are
separate facts. This page records material limits rather than implementation
checklists or checkpoint history.

## Implemented foundation

The code includes GitHub review and watched workspaces; the replacement Codex
and Claude task service; WorkBench review and private discussions; managed
skills and optional CodeGraph; source-backed development; repository memory
and spec checks; private circles; Jira surfaces; and parts of Goal planning,
research, courses, and learning.

Goal conversations and accepted outcomes already exist. Repository memory
already includes sourced capture, corrections, command recipes, and user
controls. Neither should be described as an entirely future feature simply
because an old status paragraph preceded its implementation.

## Incomplete capabilities

| Area | Remaining boundary |
| --- | --- |
| Goals | Complete bounded discovery and reassessment, retention guards, unified attention, richer proposal evidence, and full journey verification. Research currently relies on prompt scope and a disposable worktree, not a proven read-only tool policy. |
| Epics | The local classification and Home drawer exist; item management, source-child import, progress, and conclusions remain planned. |
| Code & Tests | Task-bound source/test/terminal design is established, but delivery remains in progress. Broader runners need their own validated profiles. |
| DeepSeek | Offline paths and a limited local live check exist; the complete opt-in real-key gate remains open. It does not claim parity for images, web, subagents, or CodeGraph. |
| Rebase | The program-owned service exists; a standalone branch-rebase UI remains future. |

## Verification limits

Development delivery and backport chains have fixture and local verification;
that is not evidence of a complete live-provider or live-GitHub journey. Jira
live-tenant acceptance also requires separate verification. Supported CI evidence
must be complete before a draft is promoted; unsupported checks are not green.

Experimental provider APIs require compatibility checks and explicit readiness
failures. A transport connection or a model's report does not prove supported
behavior. Versions and executable fixtures belong in configuration and tests,
not copied into a public checkpoint log.

## Deliberately outside the current boundary

Independent reviewer/verifier systems, arbitrary provider/tool registries,
automatic triage fixes, implicit issue or Jira closure, automatic merges, and
broad workflow restart recovery require separately approved designs. Related
repositories do not grant transitive access or publication authority.

Future work extends the existing services. It does not restore the deleted
orchestration systems or add compatibility layers for unshipped designs.
